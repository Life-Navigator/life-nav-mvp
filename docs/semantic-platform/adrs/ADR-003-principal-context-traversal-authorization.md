# ADR-003 — Principal- and Context-Aware Traversal Authorization

**Status:** Proposed · **Date:** 2026-07-30 · **Decision deadline:** before any second principal ships
**Owners:** Security · **Reviewers:** Graph Platform, Privacy/Governance, Agent Platform
**Related findings:** REVIEW R-3 / C-2 (Critical), debt D-4 · Blocks ADR-008, ADR-011; enables multi-agent

---

## Context

`relationship_catalog.rs` states that _"traversability is a per-context policy, not a Boolean"_ and
declares `permitted_contexts` / `permitted_principals` per relationship. The generated manifest carries
neither. The Python planner reads one boolean.

_Design inference — important nuance._ A **five-context taxonomy already exists** and the team has

`live_but_undeclared: 0` independently confirms the catalog covers every live relationship type.

## Problem statement

The serving tier cannot express per-principal or per-context authorization. Any second agent reading
the manifest inherits the personal advisor's 119 traversable relationships, including no mechanism to
withhold the 19 provider/B2B types once a provider context is implemented.

## Forces and constraints

Preserve fail-closed semantics (already correct on both sides) · preserve the property that semantic
family does not itself grant traversal · avoid a policy engine heavier than the problem · manifest is
the only cross-tier contract.

## Decision drivers

Preventing accidental permission inheritance · least added complexity · auditability · versioned contract.

## Options considered

1. Current Boolean `traversable`.
2. Context-only permission.
3. Principal-only permission.
4. **Context × principal matrix.**
5. External policy engine (OPA/Cedar).
6. Hardcoded policy per agent.

**Hard blockers.** Option 1: agent #2 inherits agent #1's rights — the finding itself. Option 6:
duplicated policy diverges (the `verify_jwt` duplication precedent is on record); a diverged policy
engine is a breach with an audit trail claiming authorization.

Option 5 is _correct_ but disqualified on proportionality: a new runtime dependency and deployment
surface to express a matrix the Rust catalog already declares. Reject as unnecessary sophistication.

## Decision

**Adopt Option 4 — context × principal matrix, exported in the manifest, evaluated identically in Rust
and Python.**

This is the least complex design that prevents inheritance, and it is mostly _serialization work_: the
policy already exists in Rust and is already computed by `relationship_coverage.py`.

## Detailed design

**Principal taxonomy (initial):** `personal_advisor`, `provider_advisor`, `organization_administrator`,
`internal_audit`, `central_knowledge`, `ingestion_pipeline`. Registered in the catalog; unknown
principal → deny.

**Query-context taxonomy:** the five already declared, plus `evaluation` for ADR-004/ADR-008
diagnostic runs — which must be a _distinct_ context so diagnostics can never borrow advisor rights.

**Representation.** Each manifest relationship row gains:

```json
{
  "rel_type": "HAS_EVIDENCE",
  "family": "evidence",
  "weight": 0.9,
  "lifecycle": "implemented",
  "permitted_contexts": ["personal_advisor", "internal_audit"],
  "permitted_principals": ["personal_advisor", "internal_audit"],
  "sensitivity": "standard"
}
```

`traversable` is retained for one release as a **derived** field (`= "personal_advisor" ∈
permitted_contexts`) for backward compatibility, then removed.

**Combination rules.** Traversal permitted **iff** active principal ∈ `permitted_principals`
**AND** active context ∈ `permitted_contexts` **AND** node sensitivity permits the principal.
**Deny precedence:** any deny wins. **Missing field → deny.** Empty list → deny. Unknown value → deny.

**Node/data sensitivity interaction.** Relationship permission is necessary but not sufficient; the
node privacy class (future ADR on classification) can further restrict. Permissions never widen.

**Manifest versioning.** Adding these fields is a **v3** bump, and v3 is a **single combined change
carrying both this ADR's policy fields and ADR-011's `superclass`** (CONFLICT-3) — two sequential bumps
would force two loader migrations, two compatibility windows, and two sets of generated artifacts for
one contract boundary. Target shape:

```json
{
  "manifest_version": 3,
  "relationships": [
    {
      "rel_type": "...",
      "family": "...",
      "weight": 0.9,
      "lifecycle": "implemented",
      "permitted_contexts": ["personal_advisor"],
      "permitted_principals": ["personal_advisor"],
      "sensitivity": "standard"
    }
  ],
  "node_classes": [{ "class": "CareerGoal", "superclass": "Objective", "privacy_class": "PII" }]
}
```

The loader **rejects** a manifest version it does not understand rather than ignoring unknown fields —
ignoring is precisely how policy silently disappears, and is the mechanism that produced this finding.
v2 is accepted only during a defined transition window, then explicitly rejected.

**Agent registration.** An agent is a catalog row: id, class, permitted contexts/domains/actions.
No wildcards; no `*`; an agent needing all domains enumerates them.

**Audit logging and trace.** Every decision emits `{principal, context, action, rel_type,
assertion_ref, verdict, reason, policy_version}` with hashed tenant. Denials logged equally.

## Security implications

The core benefit. Closes the inheritance vector before it can be exercised.

## Privacy and governance implications

Makes the 19 provider/B2B and 25 sensitive relationships governable by principal rather than by
convention.

## Tenant-isolation implications

Orthogonal and unchanged — tenancy remains enforced at the Cypher level on both endpoints
(`traversal.py:108-110`). Authorization is a second, independent gate.

## Data-model implications

Manifest schema v3. No graph change.

## Scalability implications

Static data, loaded once, cached. Negligible.

## Operational implications

One CI gate added: exported policy fields must equal catalog-declared fields.

## Cost implications

Negligible.

## Developer-experience implications

Adding an agent becomes a reviewable data change rather than a code change.

## Migration plan

1. Extend the exporter; emit both new fields **and** derived `traversable` (dual-emit).
2. Add the CI fidelity gate.
3. Python loader reads the matrix; `personal_advisor` must resolve to exactly today's 119 types —
   **zero behavioural change, test-proven**.
4. Drop `traversable`; bump to v3.
5. Register principals; enforce.

## Backfill plan

None — policy is generated, not stored.

## Compatibility strategy

Dual-emit for one release; the loader accepts either shape during transition and refuses unknown
versions after.

## Rollback strategy

Revert the loader to the boolean; the manifest superset remains valid for it.

## Observability requirements

Per-principal denial rate with baseline and anomaly alert · grant/usage divergence (unexercised grants).

## Evaluation plan

Property test: full principal × context × relationship matrix asserted explicitly, so widening a grant
fails a test rather than passing silently. Regression: personal advisor traverses exactly 119 types.

## Falsification criteria

If the personal-advisor set is not exactly 119 after migration, the export is not faithful and the
migration halts.

## Acceptance criteria

Manifest fidelity gate green · 0 wildcard grants · unknown principal/context denied · personal advisor
unchanged at 119 · every decision logged.

## Non-goals

Not implementing provider retrieval (remains the open policy question). Not classifying node privacy
(separate ADR). Not adopting an external policy engine.

## Risks accepted

The matrix is coarse (relationship-type level, not instance level). Accepted: instance-level policy is
ADR-005/ADR-010 territory via confidence and review state.

## Residual uncertainty

Provider-context retrieval design remains **open** (`unresolved_policy_decisions`), and this ADR does
not resolve it — it only ensures the manifest can express the answer.

## Consequences

Multi-agent becomes possible. Until this lands, no second principal may consume the manifest.

## Follow-up work

Provider-context retrieval ADR; node privacy classification ADR; agent registry.
