# ADR-001 — Transaction Data Placement and Graph Aggregation

**Status:** Proposed · **Date:** 2026-07-30 · **Decision deadline:** before any Wave-1 provenance work
**Owners:** Graph Platform · **Reviewers:** Data Platform, Finance Domain, Security
**Related findings:** REVIEW R-1 (Critical), debt D-2 · Depends on ADR-002, ADR-004, ADR-008

---

## Context

Neo4j holds the personal life graph. Transaction data enters via Plaid, is summarized by the Rust
worker, and is written as `TransactionSummary` nodes with edges to both the user and the account.

(independently generated by `scripts/graphrag/relationship_coverage.py`, corroborating totals).

_Design inference._ 984 summary nodes yield 1,951 edges ≈ **1.98 edges per node**, consistent with two
emitters per node. Transactions are 60.8% of edges while being 39% of nodes — the edge multiplier, not
node count, drives the composition.

_Unresolved assumption._ Summary granularity (per account per period? per category?) is not established
from the repository in this pass. `TransactionSummary` naming implies aggregation already occurs;
the **period length is unverified**. Flagged in ADR_OPEN_QUESTIONS as OQ-1.

## Problem statement

The graph's fastest-growing edge class is time-series data whose growth is `users × accounts × months`,
while every other class grows as `users × life-events`. Left unchanged, the graph asymptotically
becomes a transaction store, and every graph-wide operation — traversal, quality aggregates, backup,
partitioning, provenance, deletion — pays for data with low relational-reasoning value.

## Forces and constraints

- Neo4j is not a time-series store; Postgres already holds Plaid records as system of record.
- Advisor queries need _financial state_ ("can I afford X"), which is served by aggregates, not by
  individual transactions.
- No historical relationship may be deleted until read dependencies are proven absent (standing rule).
- Must preserve: single writer, both-endpoint tenant binding, enumerable vocabulary.

## Decision drivers

Long-term graph composition · retrieval value per edge · migration reversibility · auditability ·
deletion cost.

## Options considered

1. **Continue as-is** — keep both transaction relationships.
2. **Remove only the user-anchored edge** — keep `FinancialAccount → HAS_TRANSACTION`.
3. **Account-period summary nodes only** — Option 2 plus a canonical summary granularity.
4. **Remove all transaction nodes from Neo4j** — graph holds accounts, Postgres holds everything else.
5. **Separate time-series system** (Timescale/ClickHouse) for transactions.
6. **Derived financial-state nodes** — graph holds computed state (net worth, cash-flow, savings rate),
   no transaction representation at all.

**Hard blockers.** Option 1: unbounded growth of the dominant edge class is the ten-year cliff.
Option 5: a fourth datastore for 984 nodes is disqualifying operational complexity at current scale.
Option 6: destroys auditability — a derived net-worth figure with no traceable basis is precisely the
unattributable-number problem the platform exists to eliminate.

Option 4 scores well on scalability but sacrifices semantic fidelity (no financial evidence in the
graph at all) and is poorly reversible.

## Decision

**Adopt Option 3 — account-period summary nodes only, reached via Option 2 as the first, independently
reversible step.**

1. Stop emitting `user("HAS_TRANSACTION")`. The user reaches transactions through
   `UserProfile → OWNS_ACCOUNT → FinancialAccount → HAS_TRANSACTION`, which is semantically correct:
   a user owns accounts; accounts have transactions.
2. Retain `fk("HAS_TRANSACTION", "financial_account", "account_id")`.
3. Establish and enforce a canonical summary granularity (**one node per account per calendar month**,
   pending OQ-1 confirmation).
4. Postgres remains system of record for individual transactions. The graph never holds them.

## Detailed design

Change is one line removed from `TRANSACTION_SUMMARY` in `ontology.rs`. `HAS_TRANSACTION` moves to
`lifecycle: deprecated` **for the user-anchored emitter only** — which requires the catalog to key
lifecycle by (relationship, emitter), a small extension. Traversal from a user to transactions becomes
2 hops instead of 1; traversal bounds must accommodate depth ≥ 2 for financial queries.

## Security implications

None. Fewer edges, same tenant binding on both endpoints (`traversal.py:108-110`).

## Privacy and governance implications

Positive. Transaction detail leaves the graph's blast radius; deletion cascade shrinks.

## Tenant-isolation implications

Neutral. Account-anchored path remains tenant-bound at both endpoints. Property test must be extended
to cover the 2-hop path.

## Data-model implications

`TransactionSummary` gains a declared business identity `{account_id, period_start, period_end}`
(ADR-006). Removes an edge type from the user's immediate frontier.

## Scalability implications

**Primary benefit.** Removes ~49% of current edges (964 of 1,951 user-anchored) and, more importantly,
removes the user-anchored multiplier permanently. Projected composition (design inference, assuming
current per-tenant averages of 3.7 nodes/tenant financial and 1.56 accounts/tenant):

| Scale               | Edges as-is (est.) | Edges after | Reduction |
| ------------------- | ------------------ | ----------- | --------- |
| 268 tenants (today) | 3,208              | ~2,244      | ~30%      |
| 100K tenants        | ~1.2M              | ~0.84M      | ~30%      |
| 10M tenants         | ~120M              | ~84M        | ~30%      |

The 30% is the immediate win; the durable win is that transaction edges no longer attach to the
traversal root, so per-tenant frontier size stops growing with transaction history.

## Operational implications

Smaller graph, faster full-graph aggregates, cheaper backup/restore. Existing advisor queries that
traverse `user → transaction` in one hop must be found and re-pointed **before** deprecation.

## Cost implications

Storage and query cost fall ~30% immediately; growth rate improves permanently.

## Developer-experience implications

The 2-hop path is more semantically honest and easier to explain. Slight cost: financial queries need
depth ≥ 2.

## Migration plan

1. Inventory read dependencies on `user → HAS_TRANSACTION` (grep + traversal trace + advisor query review).
2. Deprecate the user-anchored emitter (**stops new writes; existing reads unaffected**).
3. Observe one release with zero read dependency.
4. Retire; then remove historical user-anchored edges in bounded batches with dry-run and preflight.
5. Reconcile counts against expected reduction.

## Verified migration preconditions (added 2026-07-30 — investigation C)

Repository-verified; **ADR status unchanged (`Proposed`)**. Evidence:
`docs/semantic-platform/review/OQ_INVESTIGATION_FINDINGS.md` §C; fixture
`ingestion-worker/src/relationships.rs::transaction_granularity_tests`.

1. **The worker performs NO aggregation.** No period bucketing, account grouping, dedup, or replay
   consolidation. 3 records on 1 account across 2 periods produce **6 edges** (2 per record);
   account-period bucketing would produce 4. **[VERIFIED]**
2. **Granularity is controlled upstream** by whatever `finance.transactions` emits
   (`entities.rs:57-61` — `#[serde(alias = "transaction")]`). The worker is a 1:1 transformer, so the
   30% reduction estimate in this ADR depends on an upstream property, not a worker property.
3. **A record without `account_id` receives ONLY the user-anchored edge** — verified by
   `account_fk_absent_means_only_the_user_edge_is_emitted`.
4. **Therefore removal of the user-anchored edge would make such records unreachable**, and — because
   there is no `OWNS_ACCOUNT ∘ HAS_TRANSACTION` path for them — **non-reconstructible**. This
   qualifies the Rollback section's "fully reconstructible by composition" claim: it holds **only for
   records that carry an `account_id`**.
5. **REQUIRED PRECONDITION:** a census of `TransactionSummary` records with a null/missing
   `account_id`, and an explicit disposition for them, **before** the emitter is deprecated.
   **[LIVE-DEPENDENT]** — blocks WP-400 step 2.

Also verified (OQ-11): **zero serving-tier consumers name `HAS_TRANSACTION`**. One indirect consumer
exists — `allowed_edge_types` selects by family, never by name. The ADR's rejection trigger did not
fire; migration step 1 reduces to a verification step.

## Backfill plan

None. This is a removal, not a backfill. Summary-granularity normalization, if OQ-1 shows drift, is a
separate ADR.

## Compatibility strategy

Deprecation keeps existing edges readable throughout. No reader breaks at any step.

## Rollback strategy

Steps 1–3: re-enable the emitter. Step 4: re-derive user-anchored edges from
`OWNS_ACCOUNT ∘ HAS_TRANSACTION` — **the edge is fully reconstructible by composition**, which is what
makes deletion safe here and is the key reversibility argument.

## Observability requirements

Edge-count-by-type time series; per-tenant frontier size; financial-query latency at depth 1 vs 2.

## Evaluation plan

ADR-004 golden set must show **no regression** on financial query categories at depth 2. This is a
no-regression gate, not an improvement gate.

## Falsification criteria

If advisor financial queries measurably degrade at depth 2, or if a read dependency cannot be
re-pointed, Option 2 is wrong and Option 1 stands pending redesign.

## Acceptance criteria

- Zero read dependencies on the user-anchored edge, evidenced
- No golden-set regression on financial categories
- Edge count falls within 5% of the projected ~30%
- Cross-tenant edges remain 0
- Total node count unchanged (this ADR removes no nodes)

## Non-goals

Not changing Plaid ingestion. Not introducing a time-series database. Not removing `TransactionSummary`
nodes. Not altering `OWNS_ACCOUNT`.

## Risks accepted

2-hop financial traversal costs latency. Accepted: bounded traversal makes this predictable, and the
alternative is unbounded edge growth.

## Residual uncertainty

OQ-1 (summary granularity unverified). If granularity is finer than monthly, the reduction estimate is
conservative and the case strengthens.

## Consequences

The graph becomes a relationship substrate rather than a transaction ledger. Provenance (ADR-002)
becomes materially cheaper because the highest-volume edge class shrinks.

## Follow-up work

ADR-006 business identity for `TransactionSummary`; summary-granularity normalization if OQ-1 requires.

## Superseded documents

Supersedes the implicit assumption in `SEMANTIC_DATA_MODEL.md` §1.1 that current transaction modelling
is acceptable.
